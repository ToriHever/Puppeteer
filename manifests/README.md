# Реестр скриптов

Этот каталог — машиночитаемый "реестр скриптов" для веб-интерфейса (ServisesVI):
каждый `*.json` описывает один запускаемый скрипт этого репозитория (команда,
параметры, входные/выходные файлы, нужные env-переменные, известные проблемы).
Формат описан в [SCHEMA.md](./SCHEMA.md), список всех скриптов — в [index.json](./index.json).

Backend ServisesVI может просто читать этот каталог (по пути из `.env`/submodule)
и строить форму запуска под каждый манифест, без доработок при появлении нового
скрипта — достаточно добавить новый `<id>.json` и прописать его в `index.json`.

## Прежде чем подключать к веб-UI — исправить

Эти проблемы всплыли при обзоре кода и мешают тупому запуску "как дочерний процесс":

1. ✅ **Исправлено.** `Parser_request/config.js` — `BASE_PATH` вычисляется через
   `import.meta.url` (путь к самому файлу), а не захардкожен под конкретного
   пользователя Windows. Безопасно для переноса на VDS.
2. ✅ **Исправлено.** `serch_links/package.json` — добавлено `"type": "module"`
   (код использует `import`, а package.json раньше не объявлял это).
3. ✅ **Исправлено.** `Notifications_Telegram.js` — токен и chat_id Telegram
   читаются из корневого `.env` (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`) через
   `process.env.*`, значения больше не лежат в коде открытым текстом.
   **Важно:** старый токен `7699817020:AAEVkRJJ-AoftwQMf5YI7TwAxO3g3JW1tMU` уже
   есть в истории git (в прошлых коммитах) — он считается скомпрометированным.
   Рекомендуется отозвать/перевыпустить токен у @BotFather и положить новый
   только в `.env` (который в `.gitignore`).
4. **`Parser_Meta/run_parser_meta.sh`** ссылается на `domens.txt`, а сам
   `parser_meta.js` читает `urls_meta.txt` — несовпадение имён между обёрткой
   и скриптом.
5. **Notepad-зависимость** (`Screen_SERP/screen_serp.js`, `Parser_Meta/parser_meta.js`) —
   оба шеллятся в `notepad.exe` и ждут его закрытия перед стартом. На headless
   VDS это не сработает: веб-UI должен редактировать входной файл сам, минуя
   Notepad.
6. **Ручные шлюзы** (капча/логин) — `google_ddosguard`, `multi_search_parser`,
   `serch_links`, `Parser_Meta` ждут Enter в консоли после ручного решения капчи
   в видимом браузере. Backend должен уметь стримить stdout и принимать "продолжить"
   через тот же канал, что видит статус процесса (см. исходную схему: SSE/WebSocket
   + кнопка "Продолжить"/"Повторить").

## Статус

Манифесты описывают текущее поведение скриптов "как есть". После слияния 24
коммитов из origin/main манифесты `serch_links`, `multi_search_parser` и
`tf_analysis` были пересмотрены и обновлены под новый функционал (режим
доменов×слов, раскрытие ИИ-ответа, авто-LSI/кластеризация и сборка в Excel).
При дальнейших изменениях этих трёх скриптов (и остальных) не забывай
актуализировать соответствующий `<id>.json`, иначе реестр начнёт врать
веб-интерфейсу о реальных входах/выходах скрипта.

Следующий шаг (когда будешь готова) — решить, что переносить в ServisesVI
(backend запускает эти скрипты через `child_process.spawn` по манифесту) и
когда чинить пункты 4-6 выше.
