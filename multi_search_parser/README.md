## Определение типа запроса (Коммерческий/Информационный/Полукоммерческий)

Тип запроса определяется в `parsers/base.js` (`determineQueryType`) двумя сигналами, по приоритету:

1. **Ключевые слова в самом запросе** (`utils/queryIntent.js`) — прямой сигнал. Если в тексте запроса есть явный маркер («купить», «цена», «заказать» → Коммерческий; «что такое», «как», «инструкция» → Информационный) — используется он. Если маркеров нет или они противоречат друг другу — переходим к пункту 2.
2. **Состав выдачи** (запасной вариант) — для каждой страницы в органике определяется тип по URL (`utils/pageClassifier.js`: известные инфо-домены/пути → «Информационная», `/shop`, `/price`, `/catalog` и т.п. → «Коммерческая», голая главная страница домена → «Коммерческая», иначе — «Непонятная»). Затем считается доля коммерческих страниц: `>60%` → Коммерческий, `≤40%` → Информационный, между — Полукоммерческий.

⚠️ **Исправлена ошибка**: раньше среди коммерческих паттернов был `'/'`, который совпадал (по `.includes()`) с *любым* http(s)-URL — из-за этого категория «Непонятная» была недостижима, и почти все страницы, не попавшие под инфо-паттерны, автоматически считались коммерческими, что завышало коммерческость запросов. Теперь URL разбирается на hostname/pathname, а «главная страница» проверяется явно (пустой путь), а не подстрокой по всему адресу.

## Скриншоты выдачи (опционально)

Модуль `utils/screenshot.js` умеет сохранять полный скриншот страницы выдачи по каждому запросу. Функция отдельная и подключается по желанию — по умолчанию выключена.

**Как включить:**
- Флагом при запуске: `node index.js --engine=yandex --screenshots` (или `--no-screenshots`, чтобы явно выключить и не показывать вопрос).
- Если флаг не передан — при старте задаётся отдельный вопрос «Делать скриншоты выдачи?» (1 — Да, 2 — Нет), сразу после выбора поисковой системы.

**Куда сохраняются:** `results/<движок>/screenshots/` — отдельная папка, не пересекается с CSV-результатами (`results/<движок>/results.csv`).

**Имя файла:** `<запрос> <ДД ММ ГГГГ>.png` — например, `ddos guard купить 31 07 2026.png`. Символы, недопустимые в имени файла на Windows (`\ / : * ? " < > |`), заменяются на `_`. Дата — без времени, чтобы при повторном запуске в тот же день скриншот по тому же запросу перезаписывался, а не плодил дубликаты.

Перед снимком страница докручивается до конца — часть блоков выдачи (например, у Google) дорисовывается лениво при скролле и иначе не попадёт в `fullPage`-скриншот.

## Расширенные элементы выдачи (опционально)

Модуль `utils/serpFeatures.js` для каждого запроса определяет, какие расширенные элементы показаны в выдаче: ИИ-обзор, картинки, видео, боковая панель (Knowledge Panel), похожие вопросы. Работает для обоих движков, но по-разному, т.к. разметка у них принципиально разная:

- **Yandex** — надёжно, через атрибут `data-fast-name`, которым Yandex явно помечает виджеты в DOM: `images` → картинки, `video`/`video-unisearch` → видео, `neuro_answer` → ИИ-ответ (YandexGPT), `entity_search` → карточка объекта (боковая панель), `related` → похожие запросы.
- **Google** — best-effort, разметка обфусцирована и не даёт прямых меток. Используются заголовки блоков (`#search [role="heading"]/h2/h3` — например, «Видео», «Вопросы по теме») и известные контейнеры (`g-scrolling-carousel` для картинок, `#rhs`/`.kp-wholepage` для панели). ИИ-обзор — самый ненадёжный сигнал: Google показывает ярлык «Обзор от ИИ» даже когда обзор не сгенерирован (текст «...недоступен для этого запроса»), поэтому детектор явно проверяет отсутствие этой фразы. Google также активнее блокирует автоматизацию — при капче (см. существующий флоу капчи) корректных данных не будет, это ожидаемо и не баг детектора.

**Как включить:**
- Флагом: `node index.js --engine=yandex --serp-features` (или `--no-serp-features`).
- Если флаг не передан — отдельный интерактивный вопрос при старте.

**Куда сохраняются:** `results/<движок>/serp_features.csv` — отдельный файл, колонки: `Запрос, ИИ-обзор, Картинки, Видео, Боковая панель, Похожие вопросы, checked_at` (Да/Нет).

## Распаковка обёрнутых ссылок Google (`goto?url=`)

В какой-то момент Google начал отдавать часть органических ссылок не напрямую, а обёрнутыми в `https://www.google.com/goto?url=<opaque-токен>`. Проверено вживую: это обычный HTTP 302-редирект на реальный адрес, поэтому `utils/resolveGoogleRedirects.js` распаковывает такие ссылки простым `fetch` (без браузера, без изменения `google.js`/селекторов).

Резолвинг выполняется **после** основного цикла по запросам (когда `this.results` уже полностью собран в `base.js`) — специально, чтобы не трогать и не тормозить сам процесс сбора данных внутри `searchQuery()`. На обычные (не обёрнутые) ссылки не влияет и не делает по ним лишних запросов — Yandex и уже прямые ссылки Google проходят мимо без сети.

- Работает с ограничением параллелизма (по умолчанию 8 одновременных запросов) и кэшированием одинаковых обёрнутых ссылок.
- При неудаче резолва (таймаут/невалидный токен) строка не теряется — просто остаётся с исходной обёрнутой ссылкой.
- Исходная обёрнутая ссылка сохраняется в поле `originalUrl` (не попадает в CSV, но доступна в объекте результата — на будущее, если понадобится).
- Также вызывается в `saveIntermediateResults()`, чтобы промежуточный CSV при прерывании (Ctrl+C/ошибка) тоже содержал распакованные ссылки.

## Колонка «Домен» в `results.csv`

В `utils/files.js` (`saveToCSV`) добавлена последняя колонка **Домен** — голый хост из `URL` (без `www.` и без пути), например `sweb.ru`. Считается уже из финального (распакованного) URL, так что для бывших `google.com/goto?url=...` ссылок в этой колонке окажется реальный домен, а не `google.com`. Если URL невалидный — колонка остаётся пустой, запись не падает.
